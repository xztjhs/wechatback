# WeChatBack 方案设计

> 版本：v0.1（2026-10-22）
> 状态：设计存档
> 适用：Windows 11 + 微信 4.1.15.13（Weixin.exe）
>
> 说明：本文保留项目初期的设计与决策过程。当前实现以 `README.md`、`docs/07-实战复盘与经验.md` 和 `src/wechatback/` 为准。文中 VSS 为可选增强方案，`manifest.db`、`image_key.bin` 为早期命名；实际实现使用只读连接、`archive.db` 的 `media` 表和 `image_key.json`。

---

## 0. 结论摘要

推荐采用 **“只读采集 → 解密归一 → SQLite 事实层 → Markdown 阅读层 → Obsidian 检索”** 的架构：

1. **不复制原始镜像**。数据库用 VSS 快照或临时副本读取，用完即删；`msg/attach` 里的图片直接只读解密。
2. **事实层是 `archive.db`（SQLite）**。所有消息、会话、媒体映射先入库；Markdown 只是它的确定性渲染结果，随时可重建。
3. **阅读层是 Obsidian Vault**。每个会话按月一个 Markdown，YAML frontmatter 兼容 Dataview，图片用相对路径内嵌，中文可直接全局搜索。
4. **图片全部解密为真实格式**（jpg/png/gif/webp/bmp），WXGF/HEVC 用 ffmpeg 转码；缩略图单独存一份，正文默认显示缩略图、点击看原图。
5. **视频/文件按 B 模式去重复制**：每个 SHA-256 只复制一份到 `20_Media/Videos`、`20_Media/Files`，Vault 完全自包含；同时保留清单，必要时仍可用本机只读媒体网关 `http://127.0.0.1:8765/media/<sha256>` 调用。
6. **增量靠水位 + 回看窗口 + 月度全量对账**。群聊新消息、新分片、新会话都能自动补齐；撤回/编辑会更新归档，但不会删除历史备份。

| 文件 | 1,604 PDF（6.14 GB）、898 DOCX、357 PPTX（4.46 GB）、1,236 XLSX 等（明文） |
| 会话附件目录 | 1,906 个 |
| 本机环境 | 未装 Python/ffmpeg；有 `uv`、`rg`；当前 shell 非管理员 |

### 1.2 已确认的技术事实

**数据库**：微信 4.x 使用 WCDB / SQLCipher4 变体（AES-256-CBC + HMAC-SHA512，page_size=4096，reserve=80）。4.1+ 进程内存里不再缓存明文 raw key，需要只读扫描 `com.Tencent.WCDB.Config.Cipher` 对象并用 HMAC 校验，或从 passphrase 走 PBKDF2 派生。

**图片**：`.dat` 是 V2 混合结构，已用真实文件验证并跑通 30 张样本：

```text
偏移 0..14    15 字节头：
              07 08 56 32 08 07   （签名，"V2"）
              aes_size  (LE u32)  （本机样本 = 1024）
              xor_size  (LE u32)  （本机样本 = 74199）
              01
偏移 15..      AES-128-ECB 密文段，长度 = aes_size + 16
末尾          XOR 段，长度 = xor_size，单字节异或
```

**已验证的图片密钥与算法（本机 4.1.15.13）**：

- 图片 AES key = `MD5(UIN + wxid)[:16]` 的 ASCII 字节；
- UIN 从 `%APPDATA%\Tencent\xwechat\{net,net_1,ilink,roam\ilink}\kvcomm\key_<UIN>_*.statistic` 文件名取；
- XOR key = `UIN & 0xFF`；
- AES 段长度取 `aes_size + 16`（包含 PKCS#7 填充），解密后做 PKCS#7 unpad；
- 拼接 XOR 尾段；JPEG 末尾有元数据页脚，最终落盘时截断到最后一个 `FF D9`；
- 解出长度与消息 XML 的 `length` 完全一致（实测 18667、75223）；
- 30 张样本：19 张 JPEG/PNG 直接解，11 张 WXGF 用 ffmpeg 转 PNG，**30/30 成功**。

**注意**：UIN 不是账号目录后缀，也不是 `head_imgs` 目录名；必须从 `kvcomm` 的 `key_<UIN>_*.statistic` 文件名取。用错 UIN 会得到“首块像图片、整图解不开”的假象。

### 1.3 待第一阶段验证的 Go / No-Go

| 验证项 | 结果 | 说明 |
|---|---|---|
| `wcdb-key-tool` 能否在 4.1.15.13 上提取 DB key | **✅ 已验证** | 26/27 个库命中；仅 `migrate\unspportmsg.db` 无 key（正常） |
| 图片 AES key 能否离线派生并通过 PIL 校验 | **✅ 已验证** | `MD5(UIN+wxid)[:16]`，UIN 来自 kvcomm 文件名；30/30 样本成功 |
| `Msg_*` 里 type=3/43/49 的 content 能否映射到本地文件 | **✅ 已验证** | 图片/视频看 `packed_info` 的 32 位 md5；文件看 XML `md5` + `title` |
| `local_type` 的类型解析 | **✅ 已验证** | `base_type = local_type & 0xFFFFFFFF`，`subtype = local_type >> 32` |

**原则：先用 20/30 条样本跑通，再开 36 万张图的全量批处理。**

## 2. 设计原则

1. **源数据只读**。不写、不改、不移动 `D:\WeChatData\xwechat_files` 下的任何文件；不执行 `VACUUM`、不 checkpoint 原库。
2. **不落原始镜像**。DB 用 VSS 快照或 `%TEMP%` 临时副本，跑完删除；图片直接读原文件。
3. **事实与呈现分离**。`archive.db` 是唯一事实源；Markdown/JSONL 都是可重建的投影。
4. **确定性、幂等**。同样的输入重复跑，输出字节一致；用内容哈希判断是否需要重写。
5. **Obsidian 优先**。所有格式决策先问“Obsidian 能不能直接渲染、能不能搜到”。
6. **密钥隔离**。密钥、状态、日志放 `%USERPROFILE%\.wechatback\`，不进 Vault、不进 Git 仓库。
7. **可观测**。每次运行产出统计、失败清单、跳过原因；失败不静默。

## 3. 总体架构

```text
┌─────────────────────────────────────────────────────────────────────┐
│ 微信 4.1.15.13 (Weixin.exe)  —— 只读，不修改                          │
│  db_storage/*.db          msg/attach/**/*.dat      msg/video|file/**  │
└──────────┬─────────────────────────┬───────────────────────┬────────┘
           │ VSS 快照/临时副本         │ 直接只读               │ 直接只读
           ▼                         ▼                       ▼
   ┌───────────────┐         ┌───────────────┐       ┌────────────────┐
   │ DB Decryptor  │         │ Image Decoder │       │ Media Hasher   │
   │ SQLCipher4    │         │ AES+XOR+WXGF  │       │ SHA-256 去重   │
   └───────┬───────┘         └───────┬───────┘       └───────┬────────┘
           │                         │                       │
           ▼                         ▼                       ▼
   ┌─────────────────────────────────────────────────────────────────┐
   │ archive.db（SQLite）                                             │
   │ chats / messages / media / message_media / runs / state         │
   └──────────┬───────────────────────────────┬──────────────────────┘
              │ 渲染                           │ 查询
              ▼                               ▼
   ┌───────────────────────────┐      ┌───────────────────────────┐
   │ Obsidian Vault             │      │ wechatback search / serve │
   │ 10_Chats / 20_Media / 30_Index │  │ FTS5 + 媒体网关            │
   └───────────────────────────┘      └───────────────────────────┘
```

### 3.1 组件职责

| 组件 | 职责 | 关键点 |
|---|---|---|
| `collector` | 发现账号、DB 分片、媒体目录；做 VSS/临时快照 | 不写源目录；记录文件指纹 |
| `db_decrypt` | 用 per-salt key 解密 SQLCipher4 | HMAC 校验；失败不产出半成品 |
| `normalizer` | 解析 `Msg_*`、zstd、XML/protobuf、联系人映射 | 统一成消息记录 |
| `media_image` | 解 `.dat`、WXGF→JPG/GIF、生成缩略图、去重 | 先用样本验证 key |
| `media_file` | 视频/文件哈希、去重清单 | 混合模式：≤50MB 复制，视频/大文件只记账 |
| `renderer` | 从 archive.db 渲染 Markdown | 确定性、原子替换 |
| `gateway` | 本机只读 HTTP 媒体服务 | Range、127.0.0.1、按 hash |
| `state` | 水位、文件指纹、笔记哈希 | 支持断点续跑 |
| `scheduler` | 计划任务 | 单实例锁、失败通知 |

### 4.3 命名规则

- 会话目录：`<显示名> (<chat_id>)`，显示名优先 `remark` > `nick_name` > `chat_id`。
- 文件名非法字符 `\ / : * ? " < > |` 替换为 `_`；长度截断到 80 字符，冲突时追加 `~<hash8>`。
- 图片/缩略图文件名：`<sha256>.<ext>`，全局唯一，天然去重。
- 月份文件：`YYYY-MM.md`；单月消息超过阈值（默认 5,000 条或 5 MB）时拆成 `YYYY-MM-W1.md`……，并在 frontmatter 标注 `chunk`。

## 5. 格式设计

### 5.1 事实层：`archive.db`（SQLite）

放 `%USERPROFILE%\.wechatback\archive.db`（不放进 Vault，避免被 Obsidian 索引和误改）。

核心表：

```sql
CREATE TABLE accounts (
  wxid TEXT PRIMARY KEY,
  display_name TEXT,
  db_dir TEXT,
  last_seen INTEGER
);

CREATE TABLE chats (
  chat_id TEXT PRIMARY KEY,
  account TEXT,
  chat_type TEXT,              -- private / group / official / system
  display_name TEXT,
  remark TEXT,
  nick_name TEXT,
  alias TEXT,
  first_ts INTEGER,
  last_ts INTEGER,
  message_count INTEGER,
  tags TEXT,                   -- JSON array
  contact_hash TEXT            -- 显示名变化检测
);

CREATE TABLE messages (
  msg_id TEXT PRIMARY KEY,     -- srv:<chat_id>:<server_id> 或 loc:<chat_id>:<shard>:<local_id>
  chat_id TEXT NOT NULL,
  shard TEXT,                  -- message_0 / message_1 ...
  local_id INTEGER,
  server_id INTEGER,
  ts INTEGER,                  -- Unix 秒
  time_iso TEXT,               -- 2026-10-22T18:46:40+08:00
  sender_id TEXT,
  sender_name TEXT,
  is_self INTEGER,
  type INTEGER,                -- 1/3/34/43/47/49/10000...
  subtype INTEGER,
  content TEXT,
  content_hash TEXT,           -- 变更检测
  quote_msg_id TEXT,
  media_id TEXT,               -- 主媒体（图片/视频/文件）
  source_status TEXT,          -- active / recalled / missing / edited
  raw_json TEXT
);

CREATE INDEX idx_messages_chat_ts ON messages(chat_id, ts);
CREATE INDEX idx_messages_ts ON messages(ts);

CREATE TABLE media (
  media_id TEXT PRIMARY KEY,   -- sha256
  kind TEXT,                   -- image / thumb / video / file / voice / sticker
  format TEXT,                 -- jpg / png / gif / mp4 / pdf ...
  width INTEGER,
  height INTEGER,
  size INTEGER,
  export_path TEXT,            -- 相对 Vault 的路径（图片/缩略图）
  source_path TEXT,            -- 原始绝对路径（视频/文件）
  first_seen INTEGER,
  last_seen INTEGER,
  status TEXT                  -- ok / missing / failed
);

CREATE TABLE message_media (
  message_id TEXT,
  media_id TEXT,
  role TEXT,                   -- thumb / full / video / file / voice
  PRIMARY KEY (message_id, media_id, role)
);

CREATE VIRTUAL TABLE messages_fts USING fts5(
  content, sender_name, chat_name,
  tokenize='trigram'
);
```

> FTS5 的 `trigram` 对 3 个汉字以上的子串检索最稳；2 个字的关键词回退到 `LIKE '%xx%'`（Claude/CLI 里自动切换）。如果本机 SQLite 不带 trigram，回退 `unicode61` + `LIKE`。

### 5.2 交换层：JSONL（可选，但建议保留）

`%USERPROFILE%\.wechatback\export\messages.jsonl`，一行一条，供 pandas/DuckDB/LLM 使用，不进 Vault。

```json
{"msg_id":"srv:123@chatroom:987654321","chat_id":"123@chatroom","chat_name":"示例群聊","ts":1761130000,"time":"2026-10-22T18:46:40+08:00","sender_id":"wxid_a","sender_name":"成员A","is_self":false,"type":3,"subtype":0,"content":"[图片]","media":{"media_id":"ab12...","kind":"image","export_path":"20_Media/Images/2026/10/ab/ab12....jpg","thumb_path":"20_Media/Thumbs/2026/10/ab/ab12....jpg","width":1920,"height":1080}}
```

用途：跨会话统计、关键词趋势、导出 Excel、喂给 AI 做摘要。它不是 Obsidian 的主格式，但保留成本很低。

### 5.3 阅读层：Markdown

每个会话每个月一个文件，见第 6 节模板。选择理由：

- Obsidian 原生渲染、原生搜索；
- 纯文本、可 diff、可版本化；
- 增量只需重渲染受影响的月份；
- 图片用相对路径，Vault 移动后不断链；
- 不依赖任何插件也能读。

### 5.4 媒体层：图片与缩略图

| 类型 | 输出 | 说明 |
|---|---|---|
| 普通图片 `.dat` | `20_Media/Images/YYYY/MM/<sha256>.<ext>` | ext 取真实格式：jpg/png/gif/webp/bmp |
| 缩略图 `_t.dat` | `20_Media/Thumbs/YYYY/MM/<sha256>.jpg` | 统一转 JPG，正文默认显示它 |
| 高清图 `_h.dat` | 同普通图片 | 若与普通图内容不同，保留两份 |
| WXGF（HEVC） | `.jpg`（静图）/ `.gif`（动图） | ffmpeg 转码 |
| BMP/HEIC/WebP | 尽量原样；Obsidian 不稳时转 PNG/JPEG | 以“能显示”为准 |
| 表情/贴纸 | 能解则解，否则占位 `[表情]` | 不阻塞主流程 |

**绝不把 `.dat` 放进 Vault。**

### 5.5 视频/文件层：去重清单 + 本地网关

**已确认 B 模式（去重复制）**：每个 SHA-256 只复制一份到 `20_Media/Videos` / `20_Media/Files`；清单仍保留，用于去重、缺失检测和网关兜底。三种模式的取舍见 8.1。

清单条目：

```json
{"media_id":"<sha256>","kind":"video","format":"mp4","size":12345678,
 "source_path":"D:\\Backup\\MyFile\\xwechat_files\\...\\msg\\video\\2026-10\\xxx.mp4",
 "title":"现场巡检.mp4","first_seen":"2026-10-22T22:00:00+08:00",
 "message_ids":["srv:...","srv:..."]}
```

Obsidian 里的调用方式：

```markdown
[▶ 播放视频（12.3 MB）](http://127.0.0.1:8765/media/<sha256>)
[打开 PDF（6.1 MB）](http://127.0.0.1:8765/media/<sha256>)
```

网关特性：

- 只 bind `127.0.0.1:8765`；
- 按 `<sha256>` 定位，不暴露原始路径；
- 支持 `Range`，视频可拖进度；
- `Content-Disposition: inline; filename*=UTF-8''...`，浏览器直接打开/下载；
- 文件不存在返回 404 并记录 `missing`；
- 可选 `?t=<token>`，默认不启用（本机回环）。

### 5.6 为什么不用别的格式

| 格式 | 不选的理由 |
|---|---|
| CSV | 消息含换行、引号、XML、图片数组，容易坏；不适合增量 |
| HTML | 浏览好看，但体积大、难增量、难程序查询；只适合做可选的展示页 |
| DOCX/PDF | 只适合交付，不适合归档和检索 |
| 原始 `.dat`/加密库 | 不可读，违背目标 |
| 微信官方备份 | 私有加密，只能还原回微信，不能搜索/分析 |

## 6. Obsidian 适配规范

### 6.1 Vault 设置

- 用 Obsidian 直接打开 `\\NAS\Backup\WeChatBack` 作为独立 Vault。
- `设置 → 文件与链接`：
  - 新建链接格式：**相对路径**（保证可移植）；
  - 自动更新内部链接：开；
  - 默认附件位置：`20_Media/Images`（导出器仍写显式路径，不依赖它）。
- 推荐插件（可选）：**Dataview**（索引/统计）、**Omnisearch**（大 Vault 搜索更快）。

### 6.2 Frontmatter（Dataview 兼容）

```yaml
---
type: wechat-chat
account: wxid_example
chat_id: "123456789@chatroom"
chat_name: "示例群聊"
chat_type: group
month: 2026-10
chunk: null
message_count: 1234
first_ts: 2026-10-01T08:00:00+08:00
last_ts: 2026-10-22T22:31:00+08:00
participants: ["成员A", "成员B", "成员C"]
tags:
  - wechat
  - wechat/群聊
---
```

- `type` 固定 `wechat-chat`，Dataview 用它筛。
- `chat_type`：`private` / `group` / `official` / `system`。
- `tags` 由规则生成：`wechat`、`wechat/群聊` 或 `wechat/私聊`；后续可加 `客户`、`项目` 等人工标签（不会被导出覆盖，见 9.5）。

### 6.3 笔记模板

```markdown
---
type: wechat-chat
chat_id: "123456789@chatroom"
chat_name: "示例群聊"
chat_type: group
month: 2026-10
message_count: 3
last_ts: 2026-10-22T18:50:00+08:00
tags: [wechat, wechat/群聊]
---

# 示例群聊 · 2026-10

> 会话 ID：`123456789@chatroom` ｜ 本月 3 条

## 2026-10-22

- `18:46` **成员A**：这个项目下周能报价吗？
  <!-- wb:msg:srv:123456789@chatroom:987654321 -->
- `18:47` **我**：可以，明天给你初版。
  <!-- wb:msg:srv:123456789@chatroom:987654322 -->
- `18:50` **成员B**：
  [![图片](../../../20_Media/Thumbs/2026/10/ab/abcdef.jpg)](../../../20_Media/Images/2026/10/ab/abcdef.jpg)
  <!-- wb:msg:srv:123456789@chatroom:987654323 -->
```

要点：

- **时间** `HH:mm`，日期用 `## YYYY-MM-DD`。
- **发送者** 加粗；自己显示 `**我**`；群聊必须显示，私聊也显示（便于搜索）。
- **消息 ID 注释** `<!-- wb:msg:... -->`：Obsidian 不显示，导出器可据此做增量与回溯。
- **换行**：消息内换行用 `<br>`，避免 Obsidian 把多行折叠。
- **转义**：`\`、`` ` ``、`*`、`_`、`[`、`]`、`<`、`>`、行首 `#` 做最小转义。
- **引用回复**：先一行 `> 回复 **成员A**：被引用的内容`，再正文。
- **系统消息**：`> [!note] 系统消息：...`。
- **撤回**：保留原文，追加 `> [!warning] 该消息在微信中已被撤回`。
- **删除**：保留原文，追加 `<!-- wb:source=missing -->`，不删归档。

## 7. 图片解密

### 7.1 两类密钥

| 密钥 | 用途 | 来源 | 存储 |
|---|---|---|---|
| DB key（per-salt） | 解 `message_*.db` | `wcdb-key-tool` 运行时扫描 | `secrets\db_keys.json` |
| Image AES key（16 字符） | 解 V2 `.dat` | `MD5(UIN + wxid)[:16]`；UIN 来自 `kvcomm/key_<UIN>_*.statistic` 文件名 | `secrets\image_key.json` |
| Image XOR key（1 字节） | 解 `.dat` 尾段 | `UIN & 0xFF` | 同上 |

### 7.2 解码流程

```text
读 .dat
  ├─ 签名 V2 → AES-128-ECB 解 (aes_size + 16) 字节
  │            PKCS#7 unpad
  │            XOR 解 xor_size 字节（key = UIN & 0xFF）
  │            拼接 → 真实载荷
  ├─ 载荷是 JPEG/PNG/GIF/WebP/BMP → 直接落盘
  ├─ 载荷是 WXGF → 扫描 HEVC 起始码 → 提取 Annex-B → ffmpeg → PNG（首帧）
  └─ 载荷损坏/不完整 → quarantine，记录原因，不阻塞
```

细节：

- AES 段长度必须是 `aes_size + 16`；只取 `aes_size` 会得到“首块是图片、整图解不开”的假象。
- PKCS#7 unpad 必须做；实测去掉 16 字节后长度与消息 XML `length` 完全一致。
- XOR key 用账号级 `UIN & 0xFF`，不要用文件尾反推（JPEG 有元数据页脚，会误判）。
- JPEG 末尾有约 24 字节元数据页脚，最终落盘时截断到最后一个 `FF D9`。
- WXGF 转换：扫描 `00 00 00 01` / `00 00 01`，从第一个起始码取到末尾，`ffmpeg -f hevc -i ... -frames:v 1 out.png`；11/11 样本成功。
- 输出前用 PIL 实际解码校验；同一内容按解码后字节的 SHA-256 去重。

### 7.3 缩略图

- `_t.dat` 解出的图统一转 JPG（质量 85），长边不超过 480 px。
- 正文默认内嵌缩略图；原图链接指向 `20_Media/Images/...`。
- 若缩略图本身损坏，正文回退为原图或 `[图片]` 占位。

### 7.4 图片与消息的关联

优先顺序：

1. `Msg_*` 的 `message_content` / `packed_info_data` 里解析出 `md5`、`length`、`cdnurl`；
2. 用 `md5(chat_id)` 定位 `msg\attach\<md5(chat_id)>\<YYYY-MM>\Img\<md5>.dat`；
3. 匹配 `_t` / `_h` / 基名；
4. 若失败，按同会话同月份的文件列表 + 时间邻近做兜底匹配；
5. 仍失败则记录 `unmatched`，正文写 `[图片未匹配]`，不阻塞。

> 这一段的字段名以实测为准：Phase 1 先打印 20 条 type=3/43/49 的原始 content，再定解析器。

## 8. 视频/文件去重与调用

### 8.1 三种模式（决策点）

| 模式 | 做法 | 空间 | Obsidian 体验 | 适用 |
|---|---|---|---|---|
| **A. 链接制（严格符合导出范围）** | 不复制；SHA-256 清单 + 网关 | 0 额外 | 点击外部打开 | 视频/大文件 |
| **B. 去重复制（已确认）** | 每个 hash 复制一份到 `20_Media/Files|Videos` | +约 30 GB | 可内嵌播放/预览 | 真正离线备份 |
| **C. 混合** | ≤50 MB 的文件复制；视频和大文件走网关 | +约 13 GB | 文档类可直接开，视频走网关 | 销售资料多、视频大 |

**已确认 B**：视频和文件都复制一份去重后的副本，Vault 完全自包含；代价是约 +30 GB。NAS 剩余 2.6 TB，空间足够。

### 8.2 去重算法

- 对每个被消息引用的视频/文件计算 SHA-256（大文件分块读，带进度）。
- 以 `(path, size, mtime)` 做哈希缓存，避免每次重算。
- `media_id = sha256`；同一文件在多个会话出现只保留一条清单、多个 `message_ids`。
- Markdown 链接只用 `media_id`，不暴露原始路径。

### 8.3 本地网关

- 命令：`wechatback serve`；默认 `127.0.0.1:8765`。
- 路由：
  - `GET /media/<sha256>`：流式返回，支持 `Range`；
  - `GET /health`：返回运行状态、清单条数、缺失数；
  - `GET /media/<sha256>?download=1`：强制下载。
- 启动方式：登录时计划任务，或 Obsidian 启动脚本。
- 失败兜底：Obsidian 链接旁附 `file:///D:/...` 绝对路径（仅本机可用）。

## 9. 增量维护

### 9.1 状态库

`%USERPROFILE%\.wechatback\state.db`：

```sql
CREATE TABLE runs (
  id INTEGER PRIMARY KEY,
  started_at INTEGER, finished_at INTEGER,
  mode TEXT, status TEXT, stats_json TEXT
);

CREATE TABLE db_files (
  path TEXT PRIMARY KEY,
  size INTEGER, mtime INTEGER,
  salt TEXT, key_id TEXT,
  sha1_head TEXT,
  last_decrypted_at INTEGER
);

CREATE TABLE chat_state (
  chat_id TEXT PRIMARY KEY,
  last_ts INTEGER,
  last_server_id INTEGER,
  last_local_id_json TEXT,     -- {"message_3": 12345, ...}
  contact_hash TEXT,
  last_render_month TEXT
);

CREATE TABLE notes (
  chat_id TEXT, month TEXT,
  path TEXT, content_hash TEXT,
  last_rendered_at INTEGER,
  PRIMARY KEY (chat_id, month)
);

CREATE TABLE media_seen (
  sha256 TEXT PRIMARY KEY,
  source_path TEXT, size INTEGER,
  first_seen INTEGER, last_seen INTEGER
);
```

### 9.2 每次增量做什么

1. 获取单实例锁，写 `runs` 开始记录。
2. 发现账号目录、`message_*.db`（含新增分片）、`msg/attach`、`msg/video`、`msg/file`。
3. 对比 `db_files` 的 `size/mtime/sha1_head`，只解密变化的库。
4. 若某个库的 salt 没有 key：标记 `needs_key_refresh`，退出码 2，提示管理员跑 `scripts\decrypt-db.ps1`；不静默跳过。
5. 刷新联系人/会话映射（`contact.db`、`session.db`）。
6. 对每个会话表，查询 `create_time >= last_ts - 7 天` 的行（回看窗口），按 `server_id` 或 `(shard, local_id)` upsert。
7. 比较 `content_hash`：新增/编辑/撤回分别处理；不删除历史。
8. 解析新媒体，解密图片/缩略图，按 SHA-256 去重；视频/文件更新清单。
9. 重渲染受影响的 `(chat_id, month)`；内容哈希没变的文件不重写（避免 Obsidian 反复索引）。
10. 更新 `chat_state`、`notes`、`runs`，写运行日志。

### 9.3 群聊与新分片

- `Msg_<md5(chat_id)>` 可能分布在多个 `message_N.db`；每次全部分片都查，按 `server_id` 去重。
- `real_sender_id` 必须用**当前库自己的** `Name2Id` 解析，不能跨库复用 rowid。
- 新分片（如 `message_7.db`）自动纳入；`md5(chat_id)` 反查不到时，先以 `unknown_<hash>` 建临时会话，联系人库更新后自动改名。
- 群成员变化：每次刷新 `contact.db`；显示名变化时只重渲染受影响会话。

### 9.4 撤回、编辑、删除

| 情况 | 做法 |
|---|---|
| 撤回 | 微信把原消息替换为系统消息；归档保留原文，追加 `> [!warning] 已被撤回` |
| 编辑 | `content_hash` 变化 → 更新 `content`，保留 `raw_json` 旧值（可选） |
| 删除 | 本地行消失；**月度全量对账**标记 `source_status=missing`，正文保留并加注释 |
| 重复 | `msg_id` 主键 + `server_id` 去重，重复跑不产生重复行 |

### 9.5 人工标签保护

- 导出器只改自己生成的区块（`<!-- wb:auto:start -->` 到 `<!-- wb:auto:end -->`），frontmatter 里人工加的 `tags` 保留。
- 重渲染采用“读旧 frontmatter → 合并 tags → 写新文件”，避免覆盖人工整理。
- 如果整篇文件被人工改写，导出器检测 `content_hash` 不匹配时，先备份到 `quarantine/` 再重写（可配置为跳过）。

### 9.6 对账与调度

- **每日增量**：默认 12:30（午休），VSS 快照，5–10 分钟。
- **每周轻对账**：回看 14 天，修复边界。
- **每月全量对账**：扫描全部行，标记删除/编辑；耗时较长，放在周末。
- Windows 计划任务：`WeChatBack-Incremental`（每日）、`WeChatBack-Reconcile`（每月第一个周日）、`WeChatBack-Gateway`（登录时）。
- 失败通知：写日志 + 可选 Toast/邮件；连续失败 2 次在 `90_System` 外写一个 `ALERT.txt`。

## 10. 一致性与“不修改原始数据”

### 10.1 快照策略

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **VSS（首选）** | `vssadmin create shadow /for=D:`，只读 DB 文件，跑完删除 | 微信不用关，快照一致 | 需管理员 |
| 临时副本（回退） | 复制 `.db`/`-wal`/`-shm` 到 `%TEMP%`，解密后删除 | 不需要 VSS | WAL 可能未 checkpoint，最近几分钟可能缺 |
| 短暂关闭微信（兜底） | 先提 key，再退出微信，复制/解密，重开 | 一致性好 | 有中断 |

**WAL 说明**：解密器只处理主库，未 checkpoint 的 WAL 可能缺最近消息。增量用“水位 - 7 天”回看，下一次运行会补齐；首次全量建议在微信空闲时跑，或短暂退出微信。

### 10.2 只读保证

- 所有源文件用 `FileShare.ReadWrite` 只读打开；不调用任何写 API。
- 不在源目录创建临时文件、锁文件、日志。
- 运行前后抽样记录 `(path, size, mtime, sha1_head)`，`wechatback verify --no-write` 断言不变。
- VSS 快照只读挂载，删除快照不影响源卷。

### 10.3 原子写

- Markdown 先写 `*.tmp`，`Move-Item -Force` 原子替换。
- `archive.db` 用 WAL 模式；批量写入用事务。
- 中断后重跑：`state.db` 记录水位，幂等补齐。

## 11. 安全与合规

1. **仅本人本机本人账号**；不读取他人账号，不上传云端。
2. **密钥**：`secrets\` 目录 ACL 仅当前用户；图片密钥用 DPAPI（CurrentUser）加密；不进 Vault、不进 Git 仓库、不进云同步。
3. **归档**：包含他人聊天内容；`\\NAS\Backup\WeChatBack` 建议 BitLocker/VeraCrypt 或 NAS 侧加密；至少确保 SMB 共享权限仅本人。
4. **网关**：只 bind `127.0.0.1`；不监听 `0.0.0.0`；默认无 token，若担心本机其他用户，可加 `?t=`。
5. **合规**：此类解密工具处于微信 ToS 灰色地带（`chatlog` 已于 2025-10-20 被下架）；仅用于个人备份，不分发、不商用。
6. **版本风险**：微信升级可能改密钥/格式；升级后先跑 `wechatback doctor` + 20 条样本，再开全量。

## 13. 验收标准

### 13.1 文字

- `Msg_*` 行数与 `archive.db` 的 `messages` 行数一致（允许已知的重复/系统消息差异，差异清单可解释）。
- 随机抽 20 条（私聊/群聊/各类型）与微信 UI 对照，内容、时间、发送者一致。
- 中文关键词在 Obsidian 全局搜索能命中，且能定位到月份文件。

### 13.2 图片

- 抽样 200 张（含 `_t`、`_h`、普通图、WXGF）解码成功率 ≥ 99%。
- Vault 中不存在 `.dat`。
- 随机 50 张在 Obsidian 中能显示，点击能打开原图。
- 同一张图在多个会话出现时，`20_Media/Images` 只有一份。

### 13.3 视频/文件

- 同一视频在两个群出现 → `manifest.db` 只有一条，两个消息链接都能打开。
- 网关 `Range` 请求返回 206，视频可拖动。
- 源文件删除后，网关返回 404 并在清单标记 `missing`。

### 13.4 增量

- 在测试群发一条消息 → 跑增量 → 5 分钟内出现在对应月份 Markdown，且不重复。
- 撤回一条消息 → 跑增量 → 原文保留 + 撤回标记。
- 新增一个群 → 跑增量 → 自动建目录和月份文件。
- 新增 `message_7.db` → 自动发现并纳入。

### 13.5 不修改原始数据

- 运行前后抽样 100 个源文件的 `(size, mtime, sha1_head)` 完全一致。
- 源目录没有新增文件。
- VSS 快照已删除（`vssadmin list shadows` 无残留）。
