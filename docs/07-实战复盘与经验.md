## 3. 关键技术事实（最重要）

### 3.1 数据库

- 微信 4.x 使用 WCDB / SQLCipher4 变体：AES-256-CBC + HMAC-SHA512，page_size=4096，reserve=80。
- 4.1+ 进程内存里没有明文 raw key，需扫描 `com.Tencent.WCDB.Config.Cipher` 对象并用 HMAC 校验。
- 本次 26/27 个库命中；`migrate\unspportmsg.db` 无 key 属正常。
- 解密后的库是标准 SQLite，可直接 `sqlite3` 查询。

### 3.2 图片密钥（最容易踩坑）

- 图片 AES key **不是**从账号目录后缀或 `head_imgs` 目录名推导。
- 正确来源：`%APPDATA%\Tencent\xwechat\{net,net_1,ilink,roam\ilink}\kvcomm\key_<UIN>_*.statistic` 文件名里的 **UIN**。
- 派生：

```text
AES key = MD5(UIN 十进制文本 + wxid)[:16] 的 ASCII 字节
XOR key = UIN & 0xFF
```

- 用错 UIN 的典型症状：**第一块解密像图片头，但整图打不开**。
- 校验：解密后用 PIL 完整打开，不能只看魔数。

### 3.3 `.dat` V2 布局

```text
[15 字节头]
  sig = 07 08 56 32 08 07
  aes_size = LE u32
  xor_size = LE u32
  pad = 01
[AES-128-ECB 段，长度 = aes_size + 16]
[PKCS#7 unpad]
[XOR 尾段，长度 = xor_size]
```

- **AES 段必须取 `aes_size + 16`**；只取 `aes_size` 会得到“首块对、整图错”。
- 必须做 PKCS#7 unpad。
- XOR key = `UIN & 0xFF`，不要用文件尾反推（JPEG 有元数据页脚，会误判）。
- 解出长度应与消息 XML 的 `length` 一致。
- JPEG 末尾有约 24 字节页脚，最终落盘截断到最后一个 `FF D9`。

### 3.4 WXGF（HEVC 图片）

- 解出的载荷可能是 `wxgf`，内部是 HEVC。
- 处理：扫描 `00 00 00 01` / `00 00 01` 起始码，从第一个起始码取到末尾，交给 ffmpeg：

```powershell
ffmpeg -f hevc -i input.hevc -frames:v 1 output.png
```

- 静态图取首帧；动图当前也只取首帧，后续可扩展 GIF。

### 3.5 `local_type` 是位打包

```python
base_type = local_type & 0xFFFFFFFF
subtype   = local_type >> 32
```

示例：`25769803825 = (6 << 32) | 49`（文件）；`21474836529 = (5 << 32) | 49`（链接）。
只按 `local_type == 49` 判断会漏掉 90% 的富媒体。

### 3.6 媒体映射

| 类型 | 本地文件名来源 | 路径 |
|---|---|---|
| 图片 | `packed_info_data` 末尾 32 位 ASCII hex | `msg\attach\<md5(chat_id)>\<YYYY-MM>\Img\<md5>.dat` |
| 缩略图 | 同上 | `<md5>_t.dat` |
| 高清图 | 同上 | `<md5>_h.dat` |
| 视频 | XML `md5` / `originsourcemd5` → `video_hardlink_info_v4`；缺失时按 `(月份, length)` 匹配 | `msg\video\<YYYY-MM>\<file_name>.mp4` |
| 文件 | XML `md5` → `file_hardlink_info_v4`；兜底 `msg\file\<月份>\<title>` | 原文件名 |

## 4. 失败模式与修复

### 4.1 图片第一块对、整图错

- 原因：AES 段长度少取 16 字节，或少做/多做 unpad。
- 修复：`aes_len = aes_size + 16`，解密后 PKCS#7 unpad。

### 4.2 图片密钥候选失败

- 原因：UIN 错。账号目录后缀、`head_imgs` 目录名都不是 UIN。
- 修复：从 `kvcomm/key_<UIN>_*.statistic` 取 UIN，并用 PIL 完整图校验。

### 4.3 并发写 `.tmp` 冲突

- 症状：`Permission denied: \\NAS\...\xxx.tmp`。
- 原因：同一 `sha` 的多个源并发写同一个临时文件。
- 修复：临时文件名加 `pid + thread_id`，始终用唯一临时名 + `os.replace`。

### 4.4 源 `.dat` 截断

- 症状：`truncated dat` / PIL 无法识别。
- 处理：进 `quarantine`，记录原因，不阻塞；本次 1,482 张（0.64%）。

### 4.5 SMB `Path.exists()` 旧缓存（最隐蔽）

- 症状：`media` 表有记录，但 `export_path` 文件不存在；约 0.5%。
- 原因：在 SMB 上 `Path.exists()` 可能命中旧缓存；`if not out.exists(): write` 跳过了真实写入。
- 修复：**不要用 `exists()` 做写入跳过**；图片/缩略图/视频/文件一律写入或复制。
- 本次补跑：1,118 张缺失图片 → 0；10,565 张缺失缩略图 → 0。

### 4.6 文件链接断在括号

- 症状：`报表(1).xlsx` 的链接只到 `报表`。
- 原因：Markdown `](...)` 在第一个 `)` 处结束；文件名含空格/括号。
- 修复：文件链接目标用 `<...>` 包裹：

```markdown
[📎 报表(1).xlsx](<../../../20_Media/Files/<sha>_报表(1).xlsx>)
```

### 4.7 Obsidian 打开 NAS 很卡

- 原因：NAS 是 SMB，Vault 约 40 万文件，Obsidian 启动逐个索引。
- 修复：**本地工作库 + NAS 冷备**：
  - 工作库 `D:\WeChatBackVault`（Obsidian 打开）；
  - 备份盘 `\\NAS\Backup\WeChatBack`（冷备/发布）；
  - 用 `scripts\sync-vault.ps1` 同步。

## 6. 增量工作流（推荐）

```powershell
cd D:\Tools\WeChatBack

# 一条命令：增量写本地 → 同步 Vault 到 NAS → 同步系统快照到 NAS
powershell -ExecutionPolicy Bypass -File .\scripts\publish.ps1
```

等价拆解：

```powershell
.venv\Scripts\python.exe -m wechatback.cli export --incremental
powershell -ExecutionPolicy Bypass -File .\scripts\sync-vault.ps1
powershell -ExecutionPolicy Bypass -File .\scripts\sync-system.ps1
```

- `export --incremental` 使用 `state.db` 的 per-chat 水位 + 7 天回看；
- 新增分片、新会话会自动纳入；
- 撤回/编辑会更新归档，不删除历史；
- 渲染内容未变化时跳过写入。

### 微信里补下载视频/文件后

```powershell
.venv\Scripts\python.exe -m wechatback.cli retry-missing --kind video
.venv\Scripts\python.exe -m wechatback.cli retry-missing --kind file
.venv\Scripts\python.exe -m wechatback.cli media --skip-images
```

### 验收

```powershell
.venv\Scripts\python.exe -m wechatback.cli verify --no-write
```

## 8. 安全与合规

- 仅导出本人本机、本人账号。
- 密钥在 `90_System\secrets\`，不要分享 Vault 时一起给出。
- NAS 是 SMB 共享；建议 NAS 侧仅本人可读，或整目录加密。
- 不要提交密钥、`archive.db`、`*.jsonl`、日志到 Git 仓库。
- 微信升级可能改格式；升级后先跑 `doctor` + 20 条/20 张样本。
